# LLM 활용 설계자료 (E6)

**발길 · 2026 빅콘테스트 AI데이터 활용 분야 · 작성 윤지 · 초안 2026-10-09**

> ## 규정 근거
>
> 주제설명자료 「데이터 활용 규칙」:
> *"LLM 등 생성형 AI 활용 가능하며, LLM 활용 여부는 평가에 반영하지 않음 ※ 단, **LLM 활용 시 구체적인 활용 방법 및 분석 과정에 대한 설명자료 제출 필수**"*
>
> 이 문서가 그 설명자료입니다.

---

## 1. 한 줄 요약

**판단은 모델과 규칙이 하고, LLM은 이미 나온 판단을 사람 말로 푸는 자리에만 씁니다.** 위험도 산출·끊김 판정·개인 지목에 LLM이 관여하지 않습니다.

## 2. 어디에 쓰고 어디에 안 쓰는가

| | 담당 | 이유 |
|---|---|---|
| 발길의 양·질·터전 산출과 우선순위 | **모델·규칙** | 재현·검증이 가능해야 함 |
| 끊김 판정 | **모델** | 임계값이 수치로 남아야 함 |
| 충격 보정 | **규칙** | 전 연령 대조로 계산 |
| 명부 교차·정렬 | **규칙** | 개인정보가 규칙 경로에서만 움직임 |
| 상대방 가게 지목 | **규칙** | 업종 집중도 계산 |
| 근거를 사람 말로 풀기 | **LLM** | 담당자가 3초에 이해해야 함 |
| 자원 후보 우선순위 제안 | **LLM** | 맥락 판단이 필요 |
| 전화 대본·문의 문구 | **LLM** | 상황마다 달라야 함 |
| 전화·문의·방문 실행 | **사람** | 에이전트는 제안까지 |

**도구 11개 중 LLM을 쓰는 것은 `draft_outreach` 하나**입니다. 나머지 10개(`measure_breadth`, `measure_quality`, `detect_break`, `correct_shock`, `map_ground`, `rate_state`, `match_roster`, `find_counterpart`, `match_resource`, `log_outcome`)는 모델과 규칙입니다.

## 3. 왜 이렇게 나눴는가

세 가지 이유입니다.

**첫째, 검증 가능해야 합니다.** 규정은 *"분석 결과 및 제안 내용에 대한 참가자의 직접적인 검증 및 설명이 가능해야 함"*을 요구합니다. 위험도가 생성 모델에서 나오면 왜 그 값인지 재현할 수 없습니다.

**둘째, 오탐의 비용을 낮춥니다.** LLM이 판단까지 하면 틀렸을 때 추적이 안 됩니다. 판단을 수치로 남기면 틀린 건을 임계값 조정으로 되먹일 수 있습니다(종결 기록 → 임계값).

**셋째, 개인정보입니다.** 4절.

## 4. 개인정보 — LLM 입력에 무엇이 들어가는가

**돌봄 명부는 LLM에 실리지 않습니다.** 명부 교차는 규칙 경로에서만 일어나고, LLM에는 그 결과의 **집계 수준 설명**만 전달합니다.

| | LLM 입력에 | |
|---|---|---|
| 집단 식별자 (시군구 × 성 × 연령대) | 들어감 | 36칸 중 하나. 개인이 아님 |
| 발길 네 면의 값과 상태 | 들어감 | 이미 산출된 수치 |
| 끊김 종류·기간 | 들어감 | |
| 추천 자원 후보 목록 | 들어감 | 공개 데이터 |
| **이름·연락처·주소** | **안 들어감** | 명부는 규칙 경로에만 |
| **개인 단위 결제 내역** | **안 들어감** | 제공 데이터 자체가 비식별·집계 |
| **본인 등록 단골 가게의 상호** | **안 들어감** | 지목은 규칙이 하고, 문구만 LLM이 씀 |

> 제공 데이터는 원래 *"개인 및 개별 가맹점 식별이 불가능하도록 집계·비식별 형태"*로 제공됩니다. 개인정보가 LLM에 갈 경로 자체가 없고, 유일한 위험은 돌봄 명부이므로 그것을 규칙 경로에 가둡니다.

## 5. 입출력 설계

### 5.1 적용 지점 세 곳

| 지점 | 입력 | 출력 | 형식 |
|---|---|---|---|
| 근거 풀기 | 상태 판정 결과 + 네 면의 값 | 담당자용 2~3문장 | 고정 문장 틀 + 수치 슬롯 |
| 자원 제안 | 상태 + 동 터전 지수 + 자원 후보 | 후보 3개와 각각의 이유 | 목록 |
| 대본 생성 | 끊김 종류 + 상황 | 전화 도입부·문의 문구 | 자유 문장 |

### 5.2 수치는 슬롯으로 주입합니다

**생성문이 근거 수치와 어긋나는 것을 막는 방법입니다.** 수치는 LLM이 쓰게 두지 않고, 틀에 미리 뚫어 둔 자리에 계산 결과를 넣습니다.

```
"{집단}의 발길이 {기간} 동안 {변화}했습니다. {주된 이유}."
         ↑ 규칙이 채움        ↑ 규칙      ↑ 규칙      ↑ LLM
```

### 5.3 현재 구현 상태

> **〈확인하고 채울 자리〉** 이 저장소에는 `agent.py`가 없습니다(`src/balgil/`에 `data.py`·`features.py`만 있습니다). 통합본을 들고 있는 사람에게 확인한 뒤 아래 세 가지를 채웁니다.
>
> - `draft_outreach`가 실제로 LLM을 호출하는가, 아니면 고정 문장 틀인가
> - 호출한다면 모델 식별자와 호출 방식
> - 프롬프트에 실제로 들어가는 필드 (4절 표와 대조)

**확인 전까지 이 문서는 "설계"로만 서술합니다.** D5(LLM 자리 채우기 구현)를 줄이기로 했으므로(실행계획 9절) 이번 제출 범위는 적용 지점과 입출력 규격까지일 가능성이 높지만, **구현했는지 안 했는지를 확인하지 않은 채 쓰지 않습니다.** 규정이 요구하는 것은 실제로 한 일의 설명자료입니다.

## 6. 실패했을 때

| 상황 | 동작 |
|---|---|
| LLM 호출 실패·지연 | **고정 문장 틀로 그대로 출력.** 알림은 멈추지 않습니다 |
| 생성문에 수치가 섞여 나옴 | 슬롯 외 숫자는 후처리에서 제거 |
| 생성문이 근거와 다른 주장을 함 | 담당자 화면에 **원 수치를 같이 표시**해 사람이 대조 |
| 자원 후보가 비어 있음 | 추천을 생략하고 상태만 전달 |

## 7. 평가에 쓰지 않습니다

규정이 **"LLM 활용 여부는 평가에 반영하지 않음"**이라고 못박았습니다. 따라서 발표자료와 보고서에서 LLM을 성과로 내세우지 않습니다. 이 문서는 **의무를 충족하기 위한 설명자료**이고, 본문에서 LLM이 등장하는 자리는 개인정보 경계를 설명하는 7.6절 한 곳입니다.

## 8. 한계

- 생성 문구의 품질을 **정량 평가하지 않았습니다.** 담당자 수용도 조사가 필요합니다
- 적용 지점 세 곳 중 실제 호출로 구현한 것은 없습니다(5.3)
- 같은 입력에 대한 출력 변동성을 측정하지 않았습니다
